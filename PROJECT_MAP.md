### 1.2 Purpose

A single-school management SPA covering: users/staff/students, classes (with teacher-incharge and per-subject incharge),
subjects, weekly timetable, daily + monthly attendance, online quizzes (create → attempt → auto-grade → teacher marking),
a per-role dashboard, announcements (feed only), fees (data layer only) and marks (data layer only).

It is an **"UI-first" prototype**: there is no server. All reads/writes go through an in-memory mock database that is
deep-cloned from seed arrays on boot (`structuredClone`), with a simulated 350 ms network delay so loading/error/skeleton
states are real. `src/services/http.ts` (an axios instance with JWT bearer interceptor + error normalisation) exists but is
**never imported by any module** — it is pre-wiring for a backend that does not exist yet.

### 2.5 How RBAC is enforced — and its limits

| Layer | Where | Behaviour |
| --- | --- | --- |
| Route guard | `RequireAuth` (`Guards.tsx:11`) | Redirects to `/login` with `state.from` when `state.auth.isAuthenticated` is false |
| Route guard | `RequireCapability` (`Guards.tsx:39`) | Renders `<Forbidden />` (lock icon `EmptyState`) instead of the page when `can(capability)` is false |
| UI gating | `usePermissions()` in pages | `canManage = can('users.manage' / 'classes.manage' / 'subjects.manage' / 'timetable.manage' / 'quizzes.manage')`, `canTake = can('attendance.take')`, `canMark = can('quizzes.mark')`; hides or disables the corresponding buttons and shows a "View only" badge |
| Data scoping | Inside pages (`AttendancePage`, `TimetablePage`, `QuizzesPage`, dashboards) | student → own `classId`; parent → `childIds` → child's class; teacher / teacher_incharge → `user.classIds`; admin / principal / super_admin → whole school |

**Enforcement is 100 % client-side.** There is no server, so every check above is a UI/UX gate. The complete seed database
(20 users, 3 classes, 5 subjects, **108** timetable slots, **60** attendance rows, **120** marks, **9** fee structures +
**30** invoices, 2 quizzes + 6 submissions, 5 announcements) is statically imported into the JS bundle
(`src/mocks/*` → `structuredClone` at boot), so any visitor can read every role's data from devtools.

Extra leak found while scanning: `GlobalSearch` unconditionally calls `useUsers()`, `useClasses()` and `useSubjects()`
(`src/components/layout/GlobalSearch.tsx:26-28`). A **student or parent can therefore search and see every other user's
name, email and roll number**, plus every class name. The result links to `/users` (guarded → Forbidden page), but the
data is already rendered in the dropdown.

## 4. API ENDPOINTS

### 4.0 Reality check

**There are no HTTP endpoints in this project.** No backend, no router, no controller, and no `fetch`/axios call anywhere
in `src/**` (the only axios usage is the unused instance in `src/services/http.ts`). Every "endpoint" below is the
**proposed REST shape** derived 1:1 from an existing mock data-access function. The *only* endpoint path literally written
down anywhere in the codebase is `GET /api/dashboard` (`src/services/api/dashboard.ts:15`) — everything else is a naming
mapping, not implemented behaviour.

**Status** = `MOCK EXISTS` (function implemented against the in-memory DB) or `SERVER MISSING` (nothing behind it).
*Roles allowed* is derived from the capability that guards the route/UI which calls it (§2.2); for functions with no call
site it is the intended mapping of that function's capability.

## 5. DATABASE MODELS

### 5.0 Reality check

**There are no Mongoose models, no schemas, no indexes and no database.** No `mongoose` dependency, no `new Schema(`,
no `model(`, no migrations. What exists instead:

1. **TypeScript domain interfaces** in `src/types/index.ts` — the intended document shapes ("The backend (Node + Express +
   MongoDB) will eventually return these exact shapes").
2. **A `MockDatabase` aggregate** in `src/mocks/index.ts` with 11 arrays, deep-cloned via
   `structuredClone(createDatabase())` so writes never touch the seed (`src/services/mockDb.ts`).
3. **Deterministic seed builders** in `src/mocks/*.ts` — `mulberry32(hash(key))` in `src/mocks/seed.ts` gives every
   student a stable "ability" and every record a stable value, so reloads always produce the same demo school.

All ids are **plain strings**. New records get `uid(prefix)` (e.g. `u_x8f2k1a2b`, `mk_…`, `qs_…`) from `src/lib/utils.ts`;
seeds use readable ids (`u-s-01`, `c-10a`, `s-math`, `att-c-10a-u-s-01-2026-09-25`). There is **no `_id`, no `ObjectId`,
no `__v`** anywhere. Referential integrity is by convention only — no foreign keys, no cascade rules, and only some
delete paths clean up references (see §10).

## 8. AUTH FLOW

### 8.1 Login

Files: `src/pages/auth/LoginPage.tsx`, `src/features/auth/authSlice.ts`, `src/mocks/users.ts`.

1. The form is `react-hook-form` + `zodResolver(schema)` where `schema = { email: valid email, password: min 6 chars }`.
   Defaults are pre-filled: `email = 'admin@educore.test'`, `password = DEMO_PASSWORD` (`'educore123'`).
2. `onSubmit` → `dispatch(loginStart())` → `await sleep(400)` ("pretend we are calling the JWT endpoint").
3. `authenticate(email, password)` (`authSlice.ts:90`) looks the email up in the **seed array** (`src/mocks/users.ts`),
   case-insensitively, and requires `password === DEMO_PASSWORD`. So:

   - the password is **global and identical for every account**;
   - accounts created at runtime through the Users module **cannot log in** (they are pushed into the mock DB, not into the
     seed array that `authenticate()` reads);
   - an `inactive` (`status: 'inactive'`) user **can still log in** — `status` is never checked;
   - there is no lockout, no rate-limit, no password hashing, no email verification.
4. On success → `dispatch(loginSuccess({ user, token: \`mock.jwt.${user.id}\` }))`, success toast,
   `navigate(location.state?.from ?? '/dashboard', { replace: true })`.
5. On failure → inline red alert (`"That email and password combination does not match any account."`) +
   `dispatch(loginFailure('Invalid credentials'))`.
6. **"Quick demo logins"**: 7 buttons (one per `ROLE_ORDER` entry) that call `setValue('email', …)` +
   `dispatch(switchRole(role))` + a toast + `navigate('/dashboard')` — **no password at all**.
7. `RoleSwitcher` in the topbar does the same thing at any time: `switchRole` → `resetDb()` → `queryClient.clear()` →
   `navigate('/dashboard')`.

### 8.2 Register

**MISSING.** There is no sign-up screen, route, API or reducer. Accounts are only created by an admin through
`/users` → `UserFormModal` (which pushes into the in-memory mock DB only, see §10).

### 8.3 Refresh token

**MISSING.** No refresh token, no silent refresh, no axios 401 interceptor that re-authenticates, no token expiry logic.
`http.ts` (the axios instance) is not even imported anywhere.

### 8.4 Logout

`ProfileMenu` → `dispatch(logout())` → `navigate('/login')`. The reducer (`authSlice.ts:55`) clears
`user`, `token`, `isAuthenticated`, `status` and `error`.

Two gaps:

- **The React Query cache is not cleared** on logout (only `RoleSwitcher` and the "Reset demo data" item call
  `queryClient.clear()`), so one user's cached queries remain in memory after sign-out and are re-used on the next login
  if the keys match.
- The mock database singleton is not reset, so data created by the signed-out user persists (within the tab session).

### 8.5 How tokens are stored

| Question | Answer |
| --- | --- |
| Where is the token kept? | **Redux only** — `state.auth.token` (`AuthState.token: string \| null`) |
| `localStorage` / `sessionStorage`? | **No.** A regex search for `localStorage|sessionStorage` across the whole repo returns **zero matches** |
| Cookies? | **None.** No `document.cookie`, no httpOnly cookie handling |
| Is it ever sent to a server? | **No.** `http.ts` has the `Authorization: Bearer ${token}` interceptor, but `setTokenProvider()` is never called and `http` is never imported |
| Token values actually produced | boot: the literal `'mock.jwt.token'`; after login: `` `mock.jwt.${user.id}` ``; after a role switch: `'mock.jwt.token'` again |
| Consequence on refresh | Every in-memory change is lost (the mock DB is re-created from the seed via `createDatabase()`)… but because `initialState` hard-codes the admin user with `isAuthenticated: true`, **a full page reload always signs you back in as `u-admin`** — the login screen is effectively optional |
| Session expiry | **MISSING** |

### 8.6 How RBAC is enforced end-to-end

```
LoginPage / RoleSwitcher
        │ dispatch(loginSuccess | switchRole)
        ▼
Redux authSlice  ──  state.auth.user  ──┐
        │                               │
        │                        usePermissions()  →  can(capability)  →  permissions.ts P[role]
        ▼                               │
RequireAuth (Guards.tsx)                ├──► RequireCapability (route level) → <Forbidden/> or page
  isAuthenticated? ──► /login           ├──► Sidebar navigationFor(can)      → hides menu items/sections
                                        ├──► page-level `canManage` flags     → hides/disables buttons
                                        └──► in-page data scoping             → student/parent/teacher filters
```

| Step | Mechanism | File |
| --- | --- | --- |
| 1 | User + role live in Redux (`state.auth.user.role`) | `src/features/auth/authSlice.ts` |
| 2 | `can(role, capability)` consults the static `P` map | `src/lib/permissions.ts` |
| 3 | `usePermissions()` exposes `can` / `canAny` / `isSelfService` to components | `src/hooks/usePermissions.ts` |
| 4 | `RequireAuth` blocks guests; `RequireCapability` blocks the wrong role per route | `src/components/guards/Guards.tsx` |
| 5 | Sidebar hides items whose capability is missing (drops empty sections) | `src/lib/navigation.ts` + `Sidebar.tsx` |
| 6 | Pages hide/disable write actions (`canManage`, `canTake`, `canMark`) | each page |
| 7 | Row-level scoping happens **inside the pages** (student → own `classId`, parent → `childIds`, teacher → `user.classIds`) | `AttendancePage`, `TimetablePage`, `QuizzesPage`, `dashboard.ts` (`scopedStudentIds`) |

**Limits (verified):**

- Everything above runs **in the browser**. There is no server to reject a request, and the whole dataset ships in the
  bundle, so "permissions" are UX gating, not security.
- The `RoleSwitcher` (dev helper) is rendered whenever `auth.roleSwitcherEnabled` is true — and it is **hard-coded `true`
  in `initialState`** with no dev/prod check, so **any user can switch to Super Admin in two clicks** in a production build.
- `GlobalSearch` queries users/classes/subjects regardless of role (§2.5), leaking other people's data to students/parents.
- Several pages call `useUsers()` without a role check (`TimetablePage`, `AttendancePage`, `ClassDetailPage`,
  `QuizzesPage`, `UserFormModal`, `GlobalSearch`) — the scope filter is applied only when rendering.
- `isSelfService` is computed by `usePermissions()` but **no page consumes it** (the checks are hard-coded as
  `user.role === 'student'` / `'parent'` instead).

Every hook follows the same shape: a plain `async` fetch function (`fetchX`) plus a `useX()` wrapper using
`useQuery({ queryKey, queryFn, enabled? })`, and a `useCreateX/useUpdateX/useDeleteX` wrapper using `useMutation` with

Notable details:

- There is **no optimistic update** anywhere — mutations simply invalidate and refetch (each refetch pays the fake delay).
- `useUser`, `useQuiz`, `useMarks`, `useSaveMarks`, `useDeleteMark`, `useFeeStructures`, `useFeePayments`,

  `useDeleteAnnouncement` are **defined but never called** (12 dead hooks).
- `useDashboard` keys on `today()`, so the dashboard cache self-invalidates when the calendar day changes.
- Cross-entity invalidation is minimal: `useCreateClass` invalidates `classes` **and** `users`; subject mutations
  invalidate `subjects` and `classes`; everything else invalidates only its own domain.
- `queryClient.clear()` is called by `RoleSwitcher` and by "Reset demo data" in `ProfileMenu` — but **not** on logout.

### 9.5 The mock "backend" — `src/services/mockDb.ts`

| Item | Detail |
| --- | --- |
| Storage | A single module-level `let db: MockDatabase = createDatabase()` — an in-memory `structuredClone` of the seed arrays |
| Accessor | `getDb()` returns the live object; every service mutates it in place (`db.users.push(…)`, `Object.assign(slot, input)`, …) |
| Latency | `mockDelay(ms = latencyMs)` with `latencyMs = 350` by default; `setMockLatency(ms)` exists but is **never called** |
| Errors | `mockError(message)` exists to simulate failures but is **never called**; real "not found" errors are thrown directly inside the services |
| Id generation | `nextId(prefix)` → `uid(prefix)` → `` `${prefix}_${random36}${time36}` `` |
| Reset | `resetDb()` re-creates the database from the seed — used by `RoleSwitcher` and "Reset demo data" |
| Persistence | **None** — no localStorage, no IndexedDB, no MSW. A page refresh wipes every change and restores the seed |

Persistence/optimistic-UI gaps worth knowing: because mutations mutate the shared object, an `invalidateQueries` refetch
is what makes the UI reflect the change; if a mutation succeeds but invalidation is skipped, the UI can show stale data
until the 60 s `staleTime` passes.
